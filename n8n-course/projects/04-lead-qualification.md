## 1. تحليل المتطلبات

### المشكلة
فريق مبيعات من 3 أشخاص يستقبل ~50 عميلًا محتملًا أسبوعيًا من مصادر متعددة. لا يميّزون الجاد من غير الجاد، فيهدرون الوقت على غير المؤهلين ويتأخرون على المؤهلين.

### المتطلبات

| النوع | المتطلب |
|---|---|
| **وظيفي** | استقبال من مصادر متعددة (نموذج · واتساب · API) |
| **وظيفي** | تقييم آلي بقواعد قابلة للتهيئة |
| **وظيفي** | تحليل AI للنص الحر (الملاحظات · الرسالة) |
| **وظيفي** | تصنيف حراري: `HOT` · `WARM` · `COLD` · `NOT_FIT` |
| **وظيفي** | إشعار فوري للفريق عند `HOT` فقط |
| **وظيفي** | لوحة/جدول يعرض العملاء حسب الأولوية |
| **غير وظيفي** | قواعد التقييم تُعدَّل **بلا تعديل الـ workflow** |
| **غير وظيفي** | معياري وقابل لإضافة مصادر جديدة |

### معيار النجاح
> 100% من عملاء `HOT` يُتواصل معهم خلال ساعة · وقت الفرز اليدوي = صفر.

## 2. المعمارية المعيارية

```
   [نموذج]   [واتساب]   [API خارجي]
       └─────────┼─────────┘
                 ▼
      ┌──────────────────────┐
      │  Lead Intake (Main)  │  ← نقطة دخول موحّدة
      │  تطبيع · تحقق · حفظ  │
      └──────────┬───────────┘
                 ▼
          [قاعدة البيانات]  ← مصدر الحقيقة الوحيد
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
┌──────────────┐   ┌──────────────────┐
│Lead Scoring  │   │ AI Analysis (Sub)│
│    (Sub)     │   │  تحليل النص الحر │
│ قواعد رقمية  │   └────────┬─────────┘
└──────┬───────┘            │
       └──────────┬─────────┘
                  ▼
         ┌──────────────────┐
         │ تحديد الحرارة    │
         └────────┬─────────┘
                  ▼
         ┌──────────────────┐
         │ IF: HOT؟         │
         └───┬──────────┬───┘
             ▼          ▼
    ┌────────────┐  ┌────────┐
    │Notification│  │ انتظار │
    │   (Sub)    │  │ المتابعة│
    └────────────┘  └────────┘
```

### لماذا هذا التقسيم؟

| الوحدة | المسؤولية الوحيدة | لماذا منفصلة |
|---|---|---|
| **Lead Intake** | استقبال وتطبيع وحفظ | إضافة مصدر جديد لا تمس المنطق |
| **Lead Scoring** | حساب النقاط فقط | القواعد تتغير كثيرًا |
| **AI Analysis** | تحليل النص الحر فقط | قد نغيّر النموذج أو الأمر |
| **Notification** | الإرسال فقط | تغيير القناة (تيليجرام→واتساب) = عقدة واحدة |

> 🧠 **هذا هو فصل الاهتمامات عمليًا.**
> كل وحدة لها **سبب واحد للتغيير**. الوحدة التي تحسب وتحفظ وترسل لها ثلاثة أسباب — وستكسرها ثلاث مرات.

## 3. مخطط قاعدة البيانات

```sql
CREATE TABLE leads (
  id           BIGSERIAL PRIMARY KEY,
  email        TEXT UNIQUE,
  phone        TEXT UNIQUE,
  name         TEXT NOT NULL,
  company      TEXT,
  budget       DECIMAL(12,2),
  timeline     TEXT,
  message      TEXT,
  source       TEXT NOT NULL,
  score        INTEGER NOT NULL DEFAULT 0,
  temperature  TEXT NOT NULL DEFAULT 'COLD',
  ai_intent    TEXT,
  ai_summary   TEXT,
  ai_confidence DECIMAL(3,2),
  status       TEXT NOT NULL DEFAULT 'new',
  needs_human  BOOLEAN NOT NULL DEFAULT FALSE,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- ⭐ الجدول الذي يجعل النظام قابلًا للتهيئة بلا تعديل
CREATE TABLE settings (
  key        TEXT PRIMARY KEY,
  value      JSONB NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

INSERT INTO settings (key, value) VALUES
('scoring_rules', '{
  "budget":      {"50000+": 40, "20000-50000": 25, "5000-20000": 10, "below": 0},
  "timeline":    {"immediate": 30, "1-3months": 20, "later": 5},
  "has_company": 15,
  "source":      {"referral": 15, "website": 10, "whatsapp": 8, "other": 5}
}'),
('thresholds', '{"HOT": 70, "WARM": 45, "COLD": 20}');

CREATE TABLE activities (
  id         BIGSERIAL PRIMARY KEY,
  lead_id    BIGINT NOT NULL REFERENCES leads(id) ON DELETE CASCADE,
  type       TEXT NOT NULL,
  detail     JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_leads_temp    ON leads(temperature, created_at DESC);
CREATE INDEX idx_leads_status  ON leads(status);
CREATE INDEX idx_act_lead      ON activities(lead_id);
```

> 💎 **جدول `settings` هو أذكى قرار في هذا المشروع.**
> القواعد في **بيانات** لا في **منطق**. يعني:
> - العميل يعدّل معايير التأهيل بنفسه دون أن يمسّ الـ workflow
> - لا حاجة لك عند كل تعديل بسيط → **لا تصبح عنق زجاجة**
> - يمكن اختبار قيم مختلفة بسرعة
>
> **درس معماري عام:** كل ما قد يتغير حسب العميل، ضعه في إعدادات لا في كود.
> **وميزة تجارية:** نظام يستطيع العميل تهيئته يبدو أكثر احترافًا، ويقلل مكالمات الدعم عليك.

## 4. منطق التقييم

```
النقاط = نقاط الميزانية + نقاط الجدول الزمني + نقاط الشركة + نقاط المصدر
       + تعديل AI (±15 حسب نية الشراء المكتشفة)

الحرارة:
  ≥ 70 → HOT      → إشعار فوري
  ≥ 45 → WARM     → متابعة خلال 24 ساعة
  ≥ 20 → COLD     → قائمة رعاية
  < 20 → NOT_FIT  → أرشفة
```

> ⚠️ **التقييم بالقواعد أولًا، وAI كتعديل فقط.**
> **لماذا؟** لأن التقييم يجب أن يكون **قابلًا للتفسير**.
> إن سأل العميل "لماذا صُنّف هذا عميلًا ساخنًا؟" يجب أن تجيب برقم وقاعدة، لا بـ"النموذج قرر ذلك".
> **AI يضيف إشارة من النص الحر — لا يستبدل المنطق.** هذا التصميم يبني ثقة العميل بالنظام.

### مخرج AI Analysis
```json
{
  "intent": "READY_TO_BUY | RESEARCHING | PRICE_SHOPPING | NOT_INTERESTED | UNCLEAR",
  "urgency_signal": "high | medium | low",
  "score_adjustment": 0,
  "summary": "ملخص بجملة",
  "confidence": 0.0,
  "needs_human": false
}
```

## 5. الاختبار

| # | السيناريو | المتوقع |
|---|---|---|
| 1 | ميزانية 100k · فوري · شركة · إحالة | `HOT` · إشعار فوري |
| 2 | ميزانية 3k · لاحقًا · بلا شركة | `NOT_FIT` · بلا إشعار |
| 3 | نفس البريد مرتين | سجل واحد · تحديث لا إنشاء |
| 4 | نفس الجوال بصيغة مختلفة | سجل واحد (بفضل التطبيع) |
| 5 | بلا بريد وبلا جوال | رفض بتحقق واضح |
| 6 | نص حر غاضب | `needs_human: true` |
| 7 | فشل AI | يُحفظ بالنقاط القاعدية · تنبيه |
| 8 | تعديل `scoring_rules` في القاعدة | يُطبَّق فورًا **بلا تعديل الـ workflow** |
| 9 | 100 عميل دفعة واحدة | كلهم يُعالَجون بلا تجاوز حدود |
| 10 | مصدر جديد (API) | يعمل بلا تعديل المنطق |

> ⚠️ **الاختباران 8 و 10 هما اختبار المعمارية نفسها.** إن فشلا، فالنظام ليس معياريًا فعلًا مهما بدا كذلك في الرسم.

## 6. معالجة الأخطاء

| الفشل | المعالجة |
|---|---|
| فشل AI | استخدم النقاط القاعدية · `ai_confidence = null` · تنبيه |
| فشل القاعدة | Retry ×3 → DLQ → تنبيه حرج |
| فشل الإشعار | Retry → سجّل في `activities` → لا تفقد العميل |
| بيانات ناقصة | بوابة تحقق ترفض بوضوح |
| عميل مكرر | UPSERT بالبريد أو الجوال |

> ⭐ **Dead Letter Queue:** جدول `failed_leads` يحفظ البيانات الأصلية وسبب الفشل.
> **مع العميل، الفرق جوهري:** "لم نفقد أي عميل، وهذه قائمة الـ 3 التي احتاجت تدخلًا" تختلف تمامًا عن "يبدو أن بعضهم ضاع".

## 🏋️ التحدي النهائي
أضف **محرك متابعة**: العميل `WARM` الذي لم يُتواصل معه خلال 48 ساعة → تذكير للفريق.
