### 3.1 تحليل المشكلة

#### الألم الحقيقي
العميل قال "أبغى نظام"، لكن الألم الفعلي **ثلاثي**:

| الألم | الأثر |
|---|---|
| **بطء الرد** | العميل يتواصل مع منافس أسرع → صفقة ضائعة |
| **تشتت المصادر** | لا صورة موحّدة → قرارات بلا بيانات |
| **إهدار وقت الفرز** | فريق المبيعات يطارد غير الجادين |

#### التكلفة الحالية (تقدير للنقاش مع العميل)
| البند | الحساب |
|---|---|
| فرز يدوي | 3 دقائق × 50 عميل/أسبوع = 2.5 ساعة أسبوعيًا |
| ردود متأخرة | ~15% من العملاء يُفقدون |
| بلا تقارير | لا قرارات مبنية على بيانات |

#### ما لا يقوله العميل لكنه يحتاجه
| الحاجة الخفية | لماذا |
|---|---|
| **منع تكرار العميل** | نفس الشخص يراسل من قناتين → سجلان → إحراج |
| **تتبع مصدر الصفقات** | "من أين تأتي أفضل الصفقات؟" ← أهم سؤال تجاري |
| **مسار تصعيد** | العميل الغاضب لا يجوز أن يتلقى ردًا آليًا |
| **مراقبة النظام** | يجب أن يعرف قبل العميل أن شيئًا توقف |

#### معايير النجاح المقترحة
- زمن الرد الأول: **أقل من 5 دقائق** لكل القنوات
- عملاء `HOT` يُتواصل معهم خلال **ساعة**: 100%
- **صفر** سجلات مكررة
- تقرير أسبوعي آلي بمعدل التحويل حسب المصدر

### 3.3 مخطط قاعدة البيانات

```sql
-- جهات الاتصال: كيان واحد لكل شخص مهما تعددت قنواته  ⭐
CREATE TABLE contacts (
  id           BIGSERIAL PRIMARY KEY,
  email        TEXT UNIQUE,
  phone        TEXT UNIQUE,
  instagram_id TEXT UNIQUE,
  name         TEXT NOT NULL,
  company      TEXT,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT at_least_one_identifier
    CHECK (email IS NOT NULL OR phone IS NOT NULL OR instagram_id IS NOT NULL)
);

CREATE TABLE leads (
  id            BIGSERIAL PRIMARY KEY,
  contact_id    BIGINT NOT NULL REFERENCES contacts(id) ON DELETE CASCADE,
  source        TEXT NOT NULL,
  channel       TEXT NOT NULL,
  message       TEXT,
  budget        DECIMAL(12,2),
  timeline      TEXT,
  score         INTEGER NOT NULL DEFAULT 0,
  temperature   TEXT NOT NULL DEFAULT 'COLD',
  ai_intent     TEXT,
  ai_confidence DECIMAL(3,2),
  needs_human   BOOLEAN NOT NULL DEFAULT FALSE,
  status        TEXT NOT NULL DEFAULT 'new',
  first_response_at TIMESTAMPTZ,
  converted_at      TIMESTAMPTZ,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE messages (
  id          BIGSERIAL PRIMARY KEY,
  lead_id     BIGINT NOT NULL REFERENCES leads(id) ON DELETE CASCADE,
  direction   TEXT NOT NULL CHECK (direction IN ('inbound','outbound')),
  channel     TEXT NOT NULL,
  body        TEXT NOT NULL,
  is_ai       BOOLEAN NOT NULL DEFAULT FALSE,
  approved_by TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- منع المعالجة المكررة على مستوى القاعدة  ⭐
CREATE TABLE processed_events (
  event_key    TEXT PRIMARY KEY,
  lead_id      BIGINT REFERENCES leads(id) ON DELETE SET NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- السجلات التي فشلت نهائيًا — لا نفقد شيئًا  ⭐
CREATE TABLE failed_events (
  id          BIGSERIAL PRIMARY KEY,
  raw_payload JSONB NOT NULL,
  error       TEXT NOT NULL,
  node_name   TEXT,
  retry_count INTEGER NOT NULL DEFAULT 0,
  resolved    BOOLEAN NOT NULL DEFAULT FALSE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value JSONB NOT NULL
);

CREATE INDEX idx_leads_temp     ON leads(temperature, created_at DESC);
CREATE INDEX idx_leads_status   ON leads(status) WHERE status != 'closed';
CREATE INDEX idx_leads_contact  ON leads(contact_id);
CREATE INDEX idx_msg_lead       ON messages(lead_id, created_at DESC);
CREATE INDEX idx_failed_unres   ON failed_events(resolved) WHERE resolved = FALSE;
```

#### تبرير القرارات

| القرار | السبب |
|---|---|
| **فصل `contacts` عن `leads`** | ⭐ **أهم قرار في المخطط.** نفس الشخص قد يتواصل 3 مرات عبر قناتين — شخص واحد، ثلاثة طلبات. بلا هذا الفصل ستُنشئ 3 عملاء منفصلين وتحرج نفسك أمام العميل. |
| **`CHECK at_least_one_identifier`** | يمنع سجلًا بلا أي وسيلة تعريف |
| **`processed_events`** | حماية من التكرار على مستوى القاعدة — لا يمكن تجاوزها |
| **`failed_events`** | Dead Letter Queue — لا نفقد أي عميل مهما فشل |
| **`first_response_at` / `converted_at`** | تمكّن قياس معيارَي النجاح مباشرة بلا حسابات معقدة |
| **فهارس جزئية** (`WHERE`) | أصغر وأسرع — نستعلم غالبًا عن غير المغلقة فقط |
| **`is_ai` + `approved_by`** | تدقيق كامل: من كتب هذه الرسالة؟ من اعتمدها؟ |

### 3.5 منطق منع التكرار (ثلاث طبقات)

```
الطبقة 1 — مفتاح الحدث:
  event_key = hash(channel + external_message_id)
  → إن وُجد في processed_events، توقّف فورًا

الطبقة 2 — مطابقة جهة الاتصال:
  ابحث بالبريد المطبَّع (lowercase) أو الجوال المطبَّع (+966...)
  → إن وُجد: أضف lead جديدًا لنفس contact_id (لا تُنشئ جهة اتصال جديدة)

الطبقة 3 — قيود قاعدة البيانات:
  UNIQUE على email · phone · instagram_id
  → خط الدفاع الأخير الذي لا يمكن تجاوزه
```

> 🧠 **الدفاع في العمق:** ثلاث طبقات لأن كل واحدة تفشل في حالة مختلفة.
> الطبقة 1 لا تعمل إن لم يرسل المزوّد معرّفًا. الطبقة 2 تفشل إن اختلفت صيغة الكتابة. الطبقة 3 لا تفشل أبدًا.

### 3.6 حدود الرد التلقائي

```
يُرسَل الرد التلقائي فقط إذا تحققت كل الشروط:
  ✅ ai_confidence > 0.85
  ✅ needs_human = false
  ✅ sentiment != negative
  ✅ ai_intent ليس ضمن (COMPLAINT, LEGAL, REFUND)
  ✅ لم يُرسَل رد تلقائي لهذا العميل خلال آخر ساعة
  ✅ الوقت ضمن ساعات العمل (أو رسالة "خارج الدوام" محددة)

غير ذلك → طابور التصعيد البشري
```

> ⭐ **الشرط الأخير يُنسى دائمًا.** رد آلي الساعة 3 فجرًا يكشف أن النظام آلي ويقلل الثقة.
> **والشرط قبل الأخير** يمنع حلقة رد لا نهائية مع نظام آلي على الطرف الآخر — وهذه حالة حقيقية تحدث.

| 7 | ثقة AI منخفضة | تصعيد |

> **والاختبار 14 هو الاختبار الحاسم للمعمارية.** إن احتاج تعديل منطق، فالنظام ليس معياريًا فعلًا.
