# n8n Automation Mastery — دليل المنهج

> منهج عملي لبناء أنظمة أتمتة احترافية باستخدام n8n والذكاء الاصطناعي.
> **آخر تحقق تقني:** 5 سبتمبر 2026 — مقابل n8n **2.37.10** (الإصدار المستقر).

---

## 1. تحليل الجمهور (Audience Analysis)

هذه المرحلة نُفّذت **قبل** كتابة أي درس. المنهج مصمَّم على أساسها، وليس على افتراضات عامة.

### 1.1 من هو الطالب المستهدف؟

| البُعد | الوصف |
|---|---|
| **الملف الأساسي** | شخص يريد بناء أنظمة أتمتة حقيقية — لنفسه أو لعملاء يدفعون — وليس شخصًا يريد "معرفة ما هو n8n". |
| **الخلفية البرمجية** | لا يُفترض أي خلفية برمجية. لكن يُفترض **استعداد** لتعلّم JavaScript بقدر ما تحتاجه الأتمتة (وهو قدر محدود ومحدد). |
| **الجهاز** | حاسوب + اتصال إنترنت. لا يُشترط خادم في البداية. |
| **الوقت** | 6–10 ساعات أسبوعيًا. المنهج مُقسَّم إلى وحدات تُنجَز في جلسات 60–90 دقيقة. |

### 1.2 ثلاثة ملفات شخصية يخدمها المنهج

المنهج يُخدِّم ثلاثة مسارات دخول، لأن "المبتدئ" ليس نوعًا واحدًا:

| النوع | الوصف | نقطة الدخول |
|---|---|---|
| **A — المبتدئ الحقيقي** | لم يفتح n8n من قبل | Module 1، بالترتيب |
| **B — البنّاء بالنسخ** | بنى workflows تعمل، لكن عبر نسخ حلول جاهزة أو مخرجات AI. يعرف "أين يضغط" لكن لا يعرف "لماذا". ينهار عند أول خطأ غير مألوف. | Module 4 + Debugging Lab أولًا، ثم رجوع لـ 1–3 كمراجعة سريعة |
| **C — المستقل التجاري** | يريد بيع الأتمتة كخدمة | المسار الكامل + Module 12 و14 إلزاميان قبل أي عميل |

> ⚠️ **النوع B هو الأكثر شيوعًا وهو الأخطر.**
> امتلاك workflows تعمل يخلق شعورًا زائفًا بالإتقان. الاختبار الحقيقي ليس "هل بنيتَه؟" بل **"هل تستطيع إصلاحه وحدك عند الساعة الثانية صباحًا وعميلك ينتظر؟"**
> إن كنت من النوع B، ابدأ من `exercises/DEBUGGING_LAB.md` قبل أي شيء آخر. سيكشف لك مستواك الحقيقي في 30 دقيقة.

### 1.3 ما الذي يعرفه الطالب قبل البدء؟

- استخدام المتصفح، وإنشاء حسابات على خدمات ويب.
- مفهوم عام عن "برنامج يرسل بريدًا" أو "جدول بيانات".
- **لا شيء أكثر.** كل مصطلح تقني في هذا المنهج يُشرح عند أول ظهور له.

### 1.4 ما الذي **لا** يحتاج الطالب أن يعرفه؟

توفيرًا لوقته، هذه الأمور مستبعدة عمدًا لأنها لا تُحسّن قدرته على بناء أتمتة:

| مستبعد | السبب |
|---|---|
| تطوير Nodes مخصصة بـ TypeScript | نادر الحاجة؛ 99% من الحالات يحلها HTTP Request |
| نظرية قواعد البيانات العلائقية (Normalization حتى 3NF) | نتعلم القدر العملي فقط: جداول، مفاتيح، فهارس، علاقات |
| كيف تعمل الشبكات العصبية داخليًا | نتعلم استخدام LLM كواجهة API، لا بناءه |
| Kubernetes / Terraform | مبالغة لمعظم المشاريع؛ نغطي Docker + VPS + Queue Mode |
| كل الـ 400+ Node | نتعلم **كيف نقرأ أي Node جديد**، لا حفظها |

### 1.5 المهارات المكتسَبة (Learning Outcomes)

عند إنهاء المنهج، يستطيع الطالب:

1. تحويل طلب عميل غامض إلى وثيقة متطلبات ومعمارية مكتوبة.
2. بناء workflows تتعامل مع APIs غير موثَّقة جيدًا.
3. تصميم مخطط قاعدة بيانات وتنفيذ CRUD كامل من n8n.
4. بناء AI Agents بمخرجات منظَّمة (Structured Output) وذاكرة وأدوات.
5. بناء RAG على قاعدة بيانات متجهية.
6. تشخيص أي خطأ منهجيًا دون سؤال AI أو البحث العشوائي.
7. تأمين webhooks و credentials بمعايير إنتاجية.
8. نشر n8n على VPS بـ Docker مع Postgres و HTTPS ونسخ احتياطية.
9. تصميم أنظمة معيارية (Sub-workflows) قابلة للتوسع.
10. تسليم مشروع موثَّق قابل للصيانة من قِبل شخص آخر.

### 1.6 الأخطاء التي سيقع فيها الطالب (متوقَّعة ومُعالَجة)

هذه ليست تخمينات — كل خطأ منها له درس مخصص وموقع محدد في المنهج:

| # | الخطأ | الوحدة التي تعالجه |
|---|---|---|
| 1 | الخلط بين **Item واحد** و **مصفوفة داخل item** | M4 |
| 2 | استخدام `$json` داخل عقدة لا تملك سياق الـ item المتوقع | M5 |
| 3 | افتراض أن الـ Code Node يستطيع عمل `fetch()` | M6 — **لا يستطيع، أبدًا** |
| 4 | ترك أحد مخرجَي IF غير موصول → اختفاء بيانات **بصمت** | M6 |
| 5 | اختيار وضع Merge خاطئ → تكرار أو فقدان صامت | M6 |
| 6 | وضع API Key مباشرة في حقل Header بدل Credential | M12 |
| 7 | Webhook بلا مصادقة → نقطة دخول مفتوحة للعالم | M12 |
| 8 | عدم التعامل مع Webhook مكرر → بيانات مزدوجة | M11 + M13 |
| 9 | الاعتماد على "Execute Workflow" اليدوي وظن أن الـ workflow يعمل إنتاجيًا | M2 |
| 10 | بناء workflow عملاق واحد بدل وحدات | M15 |
| 11 | تجاهل Rate Limits حتى يحظر المزوّد الحساب | M7 + M11 |
| 12 | نسيان أن n8n Cloud و self-hosted يختلفان في المتاح | M14 |
| 13 | استضافة بيانات العملاء على نسخة n8n واحدة دون ترخيص | M12 — **مسألة قانونية** |

### 1.7 أسرع مسار إلى أول أتمتة حقيقية

للطالب الذي يريد نتيجة ملموسة في أول جلسة، دون تخطّي الفهم:

```
M1 (§1.3 فقط) → M2 (§2.1–2.4) → M3 (Schedule Trigger) → Project 1
```
**الزمن المتوقع:** 90–120 دقيقة → أتمتة تعمل فعليًا وتُنتج قيمة.
ثم يعود ويكمل بالترتيب. لا تبدأ Project 2 قبل إنهاء M4 و M5 كاملين.

## 2. معمارية المنهج (Curriculum Architecture)

### 2.1 المبدأ الحاكم

كل وحدة تمر بهذه الدورة، ولا تُعتبر مكتملة قبل إتمامها كلها:

```
Understand → Build → Debug → Integrate → Secure → Deploy → Monitor → Optimize → Architect
```

**لماذا هذا الترتيب تحديدًا؟**
معظم المناهج تتوقف عند `Build`. لكن الفارق بين هاوٍ ومحترف ليس في البناء — بل في الطبقات الست التي تليه. الهاوي يسلّم workflow يعمل *اليوم*؛ المحترف يسلّم نظامًا يعمل *بعد ستة أشهر* دون تدخّله.

### 2.2 المستويات الخمسة

| المستوى | الوحدات | القدرة المكتسَبة | المشروع |
|---|---|---|---|
| **1 — Foundations** | M1, M2, M3 | بناء workflows بسيطة تعمل بمشغّل صحيح | Project 1 |
| **2 — Data Fluency** | M4, M5, M6 | التحكم الكامل في شكل البيانات وتدفقها | Project 2 |
| **3 — Integration** | M7, M8, M9 | ربط أي API وأي قاعدة بيانات | Project 3 |
| **4 — AI & Resilience** | M10, M11, M12 | أنظمة ذكية لا تنهار وآمنة | Project 4, 5 |
| **5 — Production & Architecture** | M13, M14, M15 | نشر وتصميم أنظمة حقيقية | Project 6 (Capstone) |

### 2.3 هيكل كل درس

كل درس في هذا المنهج يتبع 10 مكوّنات ثابتة:

| # | المكوّن | الغرض |
|---|---|---|
| 1 | 🎯 **الهدف** | ماذا ستستطيع فعله بعد الدرس |
| 2 | 💡 **الفكرة ببساطة** | المفهوم بلغة يومية قبل أي مصطلح |
| 3 | ❓ **لماذا يهم؟** | ربط المفهوم بمشكلة حقيقية |
| 4 | ⚙️ **كيف يعمل؟** | الآلية التقنية الدقيقة |
| 5 | 🛠️ **Build Along** | بناء تشاركي خطوة بخطوة |
| 6 | 🏋️ **Challenge** | مهمة يحلها الطالب **وحده** |
| 7 | ⚠️ **Common Mistakes** | أخطاء شائعة موثَّقة |
| 8 | ⭐ **Best Practices** | ممارسات المحترفين |
| 9 | 🧪 **Mini Quiz** | 3–5 أسئلة |
| 10 | ✅ **Definition of Done** | معيار الانتقال |

### 2.4 قاعدة عدم التخطّي

> 🧠 **لا تنتقل لوحدة جديدة قبل استيفاء Definition of Done للوحدة الحالية.**
>
> "قرأت الوحدة" ≠ "أتقنتُ الوحدة".
> المعيار الوحيد المقبول: **تستطيع بناء الحل من الصفر، وشرحه لشخص آخر، وإصلاحه عند كسره عمدًا.**

## 3. نظام التقييم (Assessment System)

| الرتبة | المعيار | الاختبار العملي |
|---|---|---|
| 🥉 **Beginner** | يبني workflows بسيطة | Form → Sheets → Email يعمل من أول محاولة |
| 🥈 **Intermediate** | يتعامل مع APIs و Databases | يربط API غير موثَّق جيدًا + CRUD كامل |
| 🥇 **Advanced** | يبني AI Automations | AI Agent بمخرجات منظَّمة + ذاكرة + أدوات |
| 💎 **Professional** | يبني أنظمة إنتاجية | نظام بـ Error Handling + Security + Monitoring + Docs |
| 👑 **Architect** | يصمم معماريات كاملة | يحوّل طلب عميل غامض إلى معمارية موثَّقة قبل أي بناء |

**قاعدة التقييم:** الرتبة تُمنح بالبناء المستقل، لا بالقراءة. إن احتجت مساعدة AI لإكمال اختبار الرتبة، فأنت لم تبلغها بعد.

| الإصدار | الحالة | ماذا يعني لك |
